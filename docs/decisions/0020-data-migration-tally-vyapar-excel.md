# 0020 — Moving data in and out: Tally, Vyapar and spreadsheets

Status: accepted. Context: prompt 34, PRD FR-123, UX-08, Principle 5.

## Decision

- **One neutral shape.** Every source is read into `ImportBundle` (parties, items, documents with lines, payments, issues) in `@gst/interop`, a new pure package that depends only on `@gst/domain`. Nothing about Tally or a spreadsheet reaches the database layer. `InteropRepo` in `@gst/db` takes the bundle, so a fourth source (Zoho, Busy) is a new reader and nothing else.
- **A streaming XML reader, written by hand.** Tally exports are large, often UTF-16, and contain character references XML forbids (`&#4;`). The reader (`XmlStream`) is fed text in pieces, builds a tree only for the elements asked for (`VOUCHER`, `LEDGER`, `GROUP`, `STOCKITEM`) and hands each over the moment it closes, so a 50 MB file costs the memory of one voucher. A test streams 50,000 vouchers in pieces of 37 characters. The browser reads a file with `TextDecoderStream` after sniffing the byte order mark. A general XML parser would hold the whole tree.
- **Credit positive.** Tally writes a credit as a positive amount and a debit as a negative one. The reader keeps that until a document is built; the writer produces balanced vouchers and warns when one is not.
- **Documents are rebuilt by the engine, never copied.** An imported document is turned into a draft, priced by `buildDocument` (the same function the editor uses), saved and issued. The file's total is kept only to compare: a difference above INR 1 is reported and the engine's figure is imported. The round-off setting is chosen to land nearest the file's total. This keeps GST returns computed from one set of rules whatever came in.
- **Rates the file does not give.** A Tally voucher carries tax ledgers, not per-line rates. A line takes its stock item's rate from the master when known, and otherwise the voucher's effective rate (tax over taxable value), snapped to the nearest standard rate within 0.2 points. A voucher with several lines and no master rates says so.
- **Original numbers in an "Imported" series.** `DocumentFlowRepo.issueImported` issues a draft under the number it already has, in a series named Imported (reset never, never the default, created on first use after making sure the type has an ordinary default so Imported can never be picked as one). It posts the ledger and moves no stock: history does not change what is on the shelf. A locked period, a blank document, wrong totals and a composition business all still stop it. A clash with an existing number renames it `<number>/IMP`, then `/IMP2`, and says so. A number the GST portal would refuse (over 16 characters or odd characters) is imported as it was and warned about.
- **Dry run, then one transaction.** `plan` writes nothing and tells a person what would happen row by row; `apply` plans again inside the transaction, writes parties, units and items, then documents in date order, then payments, and either all of it or none. Receipts and payments come in as party credit, unallocated, because a file rarely says which invoice they pay.
- **Matching.** Parties match by GSTIN, then by a name with case, punctuation and company suffixes removed; items by that name. Nothing existing is changed; an existing party keeps its opening balance.
- **Tally out.** Masters (units, GST ledgers, the sales, purchases, round-off, TCS, cash and bank ledgers, party ledgers, stock items with HSN and rate) and vouchers (sales, purchases, credit and debit notes, receipts, payments). A sales-side debit note and a purchase return are both Tally "Debit Note"; the reader tells them apart by the ledger group of the line, not the voucher name. **Round-off is a line inside each voucher**, the way Tally books it, not a separate journal voucher as the prompt text suggested; the prompt's wording is recorded here as a deliberate departure. Ledger names are editable and remembered, so entries post to the ledgers a company already has.
- **Spreadsheets.** One row per line, or a header sheet and a lines sheet joined on the invoice number, read through the column-mapping machinery parties and items already use, with Vyapar's heading spellings as aliases. A "%" in a heading is spelled out first ("Discount %" is a percentage, not an amount). Dates accept `dd-mm-yyyy`, `yyyy-mm-dd` and Excel serial numbers. Every cell that is not what it should be is a problem on that line, not a zero.

## Consequences

- Nothing here has been run against TallyPrime or a real Tally or Vyapar export. The layouts come from public documentation and the vocabulary of the XML; the round trip proves the writer and reader agree with each other and that the books balance, not that Tally accepts the file. `docs/compliance/tally-interop.md` lists the checks that need the real thing.
- Imported rows are marked with `metadata_json.imported` (source, original number, reference, the file's total) so a later audit can find them.
- Cancelled and optional Tally vouchers, journals and contras are reported and not imported. Stock opening balances from Tally are not imported.
