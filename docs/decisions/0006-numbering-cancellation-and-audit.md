# 0006 — Numbering series, cancellation, period lock and audit

Status: accepted. Context: prompt 15, PRD FR-040 to FR-044, Principle 9, CR-01.

## Decision

- **A series is a set of counter rows.** `number_series` rows that share `series_key` are one logical series: one row per financial year when it resets by year, one row if it never resets. Settings changes (name, prefix, suffix, padding, start, default flags) are applied to every row of the series. A back-dated document therefore takes its own year's counter and cannot disturb another year. Rows from before this change (no `series_key`) are treated as one series per type.
- **A document's number is data, not a formula.** It is stored as text when issued. Renaming a series changes only the next number. The register stays unique on business, type and number as the backstop, and a number already in use (imported history, an old series) is skipped, never reused.
- **Which series is used:** the one named on the draft (`metadata_json.seriesKey`, set by the picker in the header), else the series marked as the default for the caller's shell (Books or Shop), else the type's default series, else the first. A new type gets a default series the first time it is needed. Two series of one type must differ in prefix or suffix, checked when settings are saved.
- **Validation happens at settings time** (`validateSeries` in `@gst/domain`): characters, tokens, and a worst-case length that counts each token at its widest, so a series cannot be saved that could later produce a number over 16 characters. `formatDocumentNumber` still throws at issue time as a last guard.
- **One writer at a time.** `issueDraft`, `cancelDocument` and `reviseIssued` run through a promise queue per `Database` object, on top of the transaction. The browser database is a single connection, so the queue costs nothing there; for Postgres it keeps the counter read-modify-write from interleaving within one process. Across processes, the unique index is the backstop and a retry picks the next number. The test issues 1,000 documents from 8 workers (each its own repository) on one database and checks 1 to 1,000 with no gap and no duplicate, on both SQLite and PGlite.
- **Multi-device groundwork (FR-044).** `settings.sync_mode` is `local` (default) or `synced`. In synced mode a device takes numbers only from a range reserved for it (`reserveRange` carves `size` consecutive numbers out of the counter using the domain's `reserve`, and `releaseRange` returns the unused tail); with no range left it numbers `PROV-0001`… from a counter that never repeats. `finaliseNumber(id)` replaces a provisional number with a real one from the counter and is the hook prompt 41 calls after sync. A provisional number is never a valid tax invoice number; sync must finalise before a document is shared. Ranges are per counter row, so they are per series and financial year.
- **Cancellation is a status change plus reversals, in one transaction.** `cancelDocument` sets status, stamp time and reason; posts contra ledger entries for the net still standing per account and party; puts stock back with opposite movements; soft-deletes payment allocations (the payment stays as money not yet applied) and returns them so the screen can warn; and cancels a reverse-charge bill's self-invoice with it. Contra entries are dated on the cancellation date. Turnover and the party's year totals already exclude anything not `issued`, so a cancelled document leaves them without extra code. A document with an IRN is refused until e-invoice cancellation exists (prompt 32).
- **Reversal works on the net, not on the original rows.** Both cancellation and revision zero the running net per (account, party) and (item, godown). That makes a second revision, or a cancellation after a revision, correct without tracking which rows were already reversed. The cost is an extra pair of rows per revision, which is the audit trail we want in the ledger.
- **Editing after issue has two paths.** Notes, terms, references and due date go through `editIssuedNotes` or the non-financial branch of `reviseIssued`: always allowed, no revision, no repost. Everything else is a financial revision: refused when e-invoiced, in a locked period without an override, for a reverse-charge bill, or when it moves the date to another financial year; otherwise it rewrites changed lines, reverses and reposts the ledger and stock dated on the document's own date, and bumps `documents.revision`. The editor classifies by comparing what is stored with what it is saving (`changedFields`), with reference numbers told apart from the rest of `metadata_json`.
- **Period lock lives in `settings` (`period_lock`)** and is checked by the repositories, not the UI, so no screen can forget it. `assertOpen` throws `PeriodLockedError` unless the caller is an owner with a reason, and then writes an audit row (`table_name = period_lock`) naming the action and the document. Lowering or removing the lock is an unlock: owner only, reason required, audited. Roles come from `ctx.role`; a local single-user install has none and is the owner.
- **The audit trail was already written by every repository write** (`writeAudit`, same transaction). This prompt adds the readers: `AuditRepo.search` (table, user, dates), `documentHistory` (the document, its lines and lock overrides) and the viewer, with a field-level before/after and a CSV export that neutralises spreadsheet formulas.
- **The editor stays mounted when it saves a new draft.** It used to navigate to the New document route to put the draft's id in the address, which remounted the editor when it was opened from Sell. It now rewrites the current route, so a pending dialog (such as the lock override) survives the first save.

## Consequences

- A migration adds `name`, `series_key`, `is_default`, `shell_default`, `start_number` to `number_series`, `used` to `number_reservations` and `revision` to `documents`. It is the first incremental migration; existing local databases upgrade in place.
- Messages from `validateSeries` are in English in the domain package. Translating them is backlog B-020.
- Reversal and revision rows add to the ledger. Reports that sum the ledger by period are unaffected (they net to the revised figures); a report that lists raw ledger rows will show the pairs.
- The queue serialises issuing inside one process. If two browser tabs of one business ever write to the same database at once, the unique index and the skip-used-numbers loop keep numbers unique, but a number may be skipped when one loses the race, leaving a gap. Multi-tab behaviour is a sync-era concern (prompt 41).
