# 0004 — Items, units and the HSN/SAC master

Status: accepted. Context: prompt 13, PRD FR-020 to FR-024, CR-07.

## Decision

- **The HSN/SAC master is versioned data, not code.** A curated CSV (`tools/hsn/source/`) is built by `pnpm hsn:build` into `packages/domain/data/hsn-v<version>.json` plus a manifest holding the row count, the SHA-256 of the exact file bytes and an Ed25519 signature. The app ships one version and loads it into `hsn_master` the first time the database opens (`lib/hsn.ts`). The data is a separate lazy chunk (about 3.5 KB gzipped for the starter set; a full master of 10,000 codes will be roughly 250 KB), so it stays out of the first-load bundle.
- **Updates need no app release, and are off by default.** `settings.hsn_update_url` is empty until the owner sets it (https only; plain http only to this machine for testing). "Check for update" fetches the manifest, compares versions numerically, downloads the file named in it, and imports only when the hash, the row count and the signature all check out against the public key that ships in the app. A failed check changes nothing. The desktop CSP gained `connect-src 'self' ipc: http://ipc.localhost https:` for this; the web app sets no CSP of its own yet.
- **Why Ed25519 through WebCrypto.** It is the same primitive the release tooling already uses, needs no dependency, and `crypto.subtle` verifies it in Node, current Chrome, Edge and Safari. The signature covers `version`, `as_of`, `count` and `sha256`, so a changed file or a changed manifest both fail.
- **Rate history is kept, never rewritten.** `planHsnImport` (pure, tested) turns an incoming version into inserts and updates: a new rate closes the old row the day before and adds a new one; an identical rate adds nothing; a correction with the same effective date updates that row; an older version slots into history. Importing the same version twice is a no-op (`rate_master_versions.version` is unique). Documents store the rate they were issued with, so history only has to explain them, never recompute them.
- **Items follow the master only until they are overridden.** `items.gst_rate_overridden` is set by the repository whenever the item's rate differs from what the master gives for its code today (a 6 or 8 digit code falls back to its 6 then 4 digit heading). The form warns when it is set; the rate change assistant only lists items where it is false.
- **Rate change assistant applies a change only when it is in force.** Items hold one current rate, so a change dated in the future is listed but cannot be applied yet. Applying uses the same bulk-edit path as everything else, so it is audited and can be undone.
- **Bulk edit is plan, apply, undo.** `planBulkEdit` (pure) computes each item's new values with integer basis-point arithmetic and half-away rounding; the preview shows exactly that plan; `applyBulkEdit` writes it in one transaction with each item's version check (anything edited since the preview fails the whole batch); `undoBulkEdit` restores only items nobody has touched since. The undo batch lives in the page, not the database, so it lasts for the session.
- **One definition of a valid item.** `validateItemInput` in `@gst/domain` is used by the form, the CSV import and `ItemRepo` (as the storage backstop). SKU and barcode are unique among live items per business, enforced by the repository for a readable message and by a partial unique index as the backstop.
- **Barcodes.** Digit-only codes of 8, 12, 13 or 14 digits are GTINs and must carry a correct check digit; other lengths and letters, digits and `. _ - /` up to 48 characters are custom codes.
- **Units.** `UQC_MASTER` lists the GST quantity codes. A business starts with ten common units; any other standard unit is added from the master, and a custom unit carries the UQC it reports as (`returnsUqc`; an unmapped custom unit reports `OTH`). A second unit stores how many primary units make one (`secondary_factor_micros`).
- **CSV import is a dry run, then one transaction.** The wizard parses (BOM, quotes, `,` `;` tab, Windows-1252 fallback), maps columns by header text (saved per header layout in `import_mappings`, so a reordered file still maps), reviews every row with its real file line number, and only then writes. `bulkCreate` validates all rows before the first insert, writes in chunks inside one transaction with an audit row per item, reports progress and stops on cancel; any failure rolls everything back. Rows with problems are never written unless the user explicitly chooses to skip them. Parties import the same way and post opening balances.
- **CSV export neutralises formulas.** Text starting with `=`, `+`, `-`, `@`, tab or carriage return gets a leading apostrophe; amounts that are negative on purpose are written as numbers. Exports use the headers the import recognises.
- **Opening stock** is posted as a stock-in movement at the opening value when an item is created. It cannot be edited on the item afterwards (inventory adjustments arrive with prompt 19).

## Consequences

- The starter master (112 codes: common chapters and every SAC heading, rates as of 22 September 2025) is **unreviewed**. A chartered accountant must replace it with a reviewed file before release (`docs/backlog.md`). The signing key made for development must also be replaced; see `docs/runbooks/hsn-master.md`.
- Items store a single current rate. A future-dated rate change on one item (as opposed to a master change) needs the effective-dated price lists of prompt 54.
- Postgres full-text search now turns `- _ / . @` into spaces before indexing, so a SKU such as `QS-77` or an email is found by its parts, as it already was on SQLite.
- v1 migrations were regenerated (no released database exists yet). Local databases made before this change need clearing and reseeding.
