# 0014 — The desktop shell: database, data location, updates and OS integration

Status: accepted. Context: prompt 23, PRD NFR-09, NFR-12, Principle 6.

## Decision

- **The database is one SQLite connection owned by Rust** (`src-tauri/src/db.rs`), replacing the Tauri SQL plugin. Every repository relies on `BEGIN … COMMIT` issued as separate statements reaching the same connection, and the plugin pools connections, so it could not promise that (the web code said so, with a note to fix it in this prompt). The new commands (`db_open`, `db_exec`, `db_close`) keep the contract of the browser's worker, `exec(sql, params, method)` returning rows and column names, over `rusqlite` with the bundled SQLite (full-text search is in it) behind a mutex, with `foreign_keys` on and WAL. Values cross as JSON: numbers are numbers, an integer past 2^53 is `{"$int": "…"}`, bytes are `{"$blob": "<base64>"}`. A second named connection (`staging`) lets a restore build its new database beside the live one exactly as the browser does. Rust tests cover a transaction across separate calls, foreign keys, FTS5 with Devanagari, 64-bit integers and blobs, scripts with trigger bodies, and bad input.
- **Where things are.** The data folder is the user's own, so no admin rights are needed and removing the app cannot touch it: `%APPDATA%\GST Desk`, `~/Library/Application Support/GST Desk`, `~/.local/share/gst-desk`. It holds `data/` (the database; a restore's new copy sits in `data/gst-desk-restore-<n>/` beside it), `backups/`, and a `location.json` pointer that always lives in the default folder so a moved data folder is found again. Documents go under the user's Documents folder in `GST Desk`. The move wizard copies `data/` and `backups/` to an empty folder outside the old one, compares file counts and sizes, and only then writes the pointer (write beside, then rename); the old folder is left in place for the person to remove. Only folders named like a restore's can be removed from outside.
- **Updates.** `tauri-plugin-updater` with the signed `latest.json` it verifies against the public key in the config; an update whose signature does not verify is refused at download and nothing is installed. The check, the background download and the restart are separate steps: a check on launch (after a short wait) and then daily; a quiet download; a bar saying "Version x is ready" with the release notes and **Restart to update**. The app never restarts under a person. The channel (stable or beta) chooses the manifest: stable reads the configured address, beta reads `beta/latest.json` beside it. Before installing, the running executable is copied to `previous/<version>/` (the last two are kept) so a bad update can be gone back from by hand, and the database is closed cleanly first. A debug build may point the check at a mock server; a release build ignores that, so nothing in a page or the environment can redirect where updates come from. The public key and address are empty in the repository: the person who owns the release key adds them (`docs/runbooks/release.md`).
- **Installers.** Windows: NSIS per user (no administrator) and MSI; macOS: a universal DMG, with the notarisation secrets already wired in CI; Linux: AppImage and deb. `verify-release.mjs` keeps every installer under 15 MB. The NSIS uninstaller shows where the data is and that it was not touched. The MSI is per machine (WiX's default) and needs administrator rights: see B-080.
- **OS integration.** Single-instance lock (a second launch hands its arguments to the first and brings it forward), window size and position remembered, the `gstdesk://` scheme and the `.gstbk` file association, a tray icon with New bill, Back up now, Open data folder, Show and Quit (labels in the language of the screens), launch at login (starts hidden in the tray), native notifications when the inbox checks find new items, and printer names for the thermal settings. A link opens only a short list of pages (inbox, dashboard, reports, a new bill, backup settings); a `.gstbk` opens the restore dialog, which still shows what is in it and asks before anything is restored; only `.gstbk` files can be read this way.
- **Problems.** Logs rotate (1 MB each, the newest five). "Report a problem" saves a ZIP of the newest logs and a machine description with emails, GSTINs, PANs, ids, long numbers and user names taken out; it never contains the database, backups, documents or settings (a test puts a database beside the logs and checks it stays out).
- **Test hooks are debug-only.** `GSTDESK_DATA_DIR` moves the data folder and the mock update address are honoured only in debug builds.

## Consequences

- The desktop and the browser run the same repositories against the same SQL; a transaction means the same thing in both.
- A moved data folder needs the pointer in the default folder to survive; if the pointer's folder is gone the app falls back to the default one rather than failing.
- Not built here: Windows jump list and macOS dock menu (the tray carries the quick actions on Windows and Linux) and a native-side cold-start budget measurement on the baseline laptop. Both are in the backlog, as is running the install matrix on the other operating systems (`docs/qa/install-matrix.md`).
