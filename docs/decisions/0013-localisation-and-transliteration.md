# 0013 — Localisation, transliteration and Indian formats

Status: accepted. Context: prompt 22, PRD FR-063, NFR-10, UX-07.

## Decision

- **English is the source; other languages are measured against it.** The screen strings (`ui`), the error strings (`errors`), the explanations (`help`) and the printed-document labels (`print`) are four i18next namespaces in `packages/i18n`. A language file holds only what has been translated; anything missing falls back to English, never to a raw key. Another language's file is loaded the first time it is chosen (`setLanguage`), so switching needs no reload and a person who stays in English never downloads another.
- **Keys are checked by the compiler.** `t()` in the web app is typed from the English catalogue (`lib/i18next.d.ts`): a mistyped key does not compile. A key built at run time (`inbox.kinds.${kind}`) goes through `dyn()`, which says so out loud. `pnpm i18n:extract` also reads every `t()` call and fails on a literal key English does not have; its first run found a real bug (a `common.cancel` that never existed).
- **The catalogue cannot silently fall behind.** `pnpm i18n:check` fails when a language lacks a string and has no draft, when a translation changes a `{{placeholder}}`, or when a language keeps a string English removed. `pnpm i18n:draft` writes drafts for the missing strings (English with the glossary's terms swapped in, marked `todo`) to `locales-todo/<lang>.json`, using only the local glossary. Drafts are never shown in the app. Both checks run in `ci:static`.
- **Honest state.** About 6 percent of the screen strings are translated in each of the five languages (navigation, chrome, the inbox, errors); the printed document and the payment reminder are complete. The rest shows in English until a translator does it. `docs/i18n/review.md` records that no language has been reviewed by a native speaker or the CA reviewer yet.
- **One glossary.** `glossary.ts` gives each GST concept one word per language. Concepts that appear on a printed document are read from the print catalogue itself (a test checks they agree), so a screen and its printout cannot use different words. Screens that show a GST name (CGST, GSTIN, HSN) take it from the glossary.
- **Transliteration is rules, not a model.** `translit.ts` converts Roman letters to Devanagari, Tamil, Bengali and Gujarati with an ITRANS-like table: consonant clusters get a halant, a final consonant keeps its inherent a (Tamil closes it with a pulli), M and H are the anusvara and visarga, and Bengali and Gujarati are produced from the Devanagari result by Unicode offset, with their few differences handled by hand. It cannot know a spelling, so `suggest()` gives the likeliest reading first and the others after it: a long final vowel first for Hindi names ending in a consonant and a (शर्मा), retroflex t and d, Tamil's long e and o. The field shows them under the text; Space or Enter takes the first, Up and Down choose, Escape keeps the letters. Tested with 50 words per script (Bengali and Gujarati against a separate offset oracle, plus hand-written words).
- **Native text plus a Roman key.** Parties and items keep the name as typed (`name`) and a Roman form (`name_latin`, from the letters typed, or worked out by `romanise` for pasted text). Search reads both: migration 9002 rebuilds the parties and items search index to include it. On Postgres the default text parser splits Devanagari at its vowel signs, so searching native script there is not reliable (B-076); the Roman key works.
- **Indian formats do not depend on the language.** Dates `dd-MM-yyyy`, lakh and crore grouping, the rupee sign touching the number (`₹1,23,456.00`, or `Rs. 1,23,456.00` where the sign cannot be shown), and financial years written `2025-26` (`format.ts`). The stored FY label (`25-26`, in document numbers) is unchanged. Amount in words has English and Hindi (Marathi reads in Hindi's words); Tamil, Bengali and Gujarati fall back to English (B-075).
- **Language per business, per party.** The business's language is the template's (existing). A party can choose their own (`parties.language`): their copy of a document prints in it, and a payment reminder is drafted in it (otherwise in the language their state suggests, which closes B-069).
- **Fonts load when needed.** The Indian-script fonts are `@font-face` rules with unicode ranges, so the browser fetches one only when text in that script is on the page; a test checks that an English session requests none.
- **Layout is checked, not hoped for.** `?lng=pseudo` shows the English made 40 percent longer; the Storybook toolbar has the same locale, and an end-to-end test walks six pages in Tamil, Bengali and the pseudo-locale at 1366 by 768 in compact density looking for horizontal overflow.
- **Text typed into JSX is a lint error** in `apps/web` (JSX text, `{'literal'}`, and aria-label, title, placeholder, alt and label attributes with two or more Latin letters). Thirty-nine existing strings were moved into the catalogue or onto the glossary; names that are the same in every language (brands, key caps, formats) live in `lib/terms.ts`.

## Consequences

- A new screen string goes in `en.ts` first; `pnpm i18n:draft` then lists it for translators. A string typed into JSX fails lint.
- Transliteration suggestions are conventions, not truth; a person always chooses, and the Roman key keeps the name findable if they choose wrong.
- Voice input is out of scope (prompt 36).
