# 0011 — Backup, restore, export, import and the trash

Status: accepted. Context: prompt 20, PRD FR-120 to FR-122, NFR-03, Principles 2 and 5.

## Decision

- **A backup is a logical copy, not a file copy.** A `.gstbk` is a ZIP: `manifest.json` (format and schema version, the businesses, a row count, size and SHA-256 for every file), one `data/<table>.jsonl` per table, and `attachments/<sha256>`. It is written and read by the same TypeScript in the browser, in Node and (later) in the desktop app, from the schema spec, so a new table is in every backup the day it is added, and a person can open one with any unzip tool. The prompt asked for the desktop to copy the SQLite file with the online backup API; that needs the Rust side, which is not verified yet (prompt 23), so it is deferred (B-059). The logical format is the one the desktop will write too, so backups move between devices and between the browser and the desktop.
- **A backup reads, never writes.** It reads each table in key order a chunk at a time with `SELECT *` (so it also works on a database one migration behind, which is what the pre-migration backup needs), encodes each chunk as it goes, compresses in 256 KB slices and gives the page a chance to run between them. Measured on a 347 MB database of 527,000 rows (`perf/backup.perf.ts`): the backup takes about 16 s, produces 51 MB, and never holds the page for more than about 200 ms. Restore takes about 47 s.
- **A restore is all or nothing, and is built beside the live database.** It checks the file first (it is a backup, every checksum and row count matches, the app is new enough), unpacks it into a second, empty database, inserts every table in one transaction in foreign-key order, compares the counts with the manifest, runs `integrity_check` and `foreign_key_check`, and only then replaces the live one. In the browser the second database is its own OPFS directory, and "replace" is one write of a pointer in `localStorage`; the old directory is kept for a week and the app goes back to it by itself if the new one will not open. In Node (and the desktop app) it is a staging file swapped in with renames; the old file becomes `<file>.previous`. A chaos test kills the process mid-restore, before the swap and between the two renames, and checks that the old database is intact or recovered each time.
- **Restore a single business** reads that business out of a full backup and imports it as a new business in the current database, so nothing else changes.
- **Export and import use new ids.** The JSON export is one business, with each document's lines inside it and each payment's allocations inside it. Importing replaces every id and every reference (including ids kept inside JSON settings, such as a saved report view), stamps the rows with the importing person, runs in one transaction, and has a dry run that does the same work and rolls it back so the counts are exactly what a real import writes. The CSV bundle has one file per table, every column, formula-safe text, and the attached files. The schema of all three is `docs/export-schema.md`, generated from the schema and checked by a test.
- **Secrets never leave.** Settings whose key marks a secret (`secret…`, `oauth…`, `cloud.token…`, `cloud.secret…`, `cloud.credentials`, `pin…`) are left out of backups and exports. A test found that the audit trail recorded those values, which would have carried them into every backup; the audit trail now records that a secret changed and not what it became, and old rows are scrubbed on the way out.
- **Backups are kept by a rule.** Automatic backups: the newest of each of the last 30 days and of each of the last 12 months is kept, never fewer than the newest one. Backups the person makes themselves are their own choice and are not thinned by day (a first version did, and deleted the backup being restored from when a safety backup was taken the same day): the newest ten are kept. The last three taken before an update are kept separately. Automatic backups run at a chosen time or on the first launch of the day, retry no more than hourly after a failure, and a failure shows on the notification bell. Every backup is checked after it is written and read back from where it was kept.
- **The pre-migration hook.** Opening a database that holds data and has migrations to apply takes a backup first; if the backup cannot be made, the update does not run and the app says why.
- **Where a browser keeps backups.** In the app's own storage (always) and, in Chromium browsers, also in a folder the person chooses (File System Access API), which is what protects against browser data being cleared. Others get "Download a backup", and a reminder every 7 days. The app says plainly, at the top of the Backup tab, that browser storage can be cleared.
- **The trash holds deleted parties, items and drafts for 30 days.** Restore brings one back (and says so if it now clashes with something added since). Deleting for good needed the database's "no hard delete" rule relaxed for exactly those rows: a new migration lets a row be removed only if it is already in the trash (and a trashed draft's lines with it). Issued documents cannot be moved to the trash, so they stay undeletable, and a live row still cannot be deleted. Purging is written to the audit trail.
- **Cloud drive** is desktop only, opt-in, and uses the person's own Google or OneDrive app (`docs/runbooks/cloud-backup.md`). The uploaders (refresh-token sign-in, resumable upload to Drive, simple or chunked upload to OneDrive) are tested against a fake network. The credentials are secret settings. The interactive sign-in that produces the refresh token belongs to the desktop shell and is deferred (B-060); until then the person pastes a refresh token.

## Consequences

- Backup, restore and import work on the local SQLite database only. A Postgres deployment is backed up with the database's own tools, and its row-level security would hide other organisations' rows from this reader.
- Restoring a backup from an older schema works (the database is migrated first and rows keep the columns they have); one from a newer app is refused with a message.
- In the browser a restore keeps both databases for a week, so storage use briefly doubles.
- Backups include the audit trail and the AI call log; the JSON and CSV exports leave them out unless asked.
